# ms-product

> 커머스 마이크로서비스 아키텍처에서 **상품 정보**를 담당하는 서비스.

판매 대상이 무엇인지 정의한다. 상품과 그 판매 형태, 선택 옵션, 분류 체계가 이 서비스의 소유다.

수량과 가격은 **의도적으로 제외했다.** 같은 대상을 가리키지만 변경 빈도와 동시성 특성이 전혀 달라서, 한 서비스에 담으면 어느 쪽이 진실인지 정할 수 없는 데이터가 생긴다.

판매 대상을 채널별로 묶어 진열하는 구성도 이 서비스 밖이다. 무엇이 존재하는가와 그것을 어디에 어떤 묶음으로 내보이는가는 서로 다른 질문이다.

이 서비스는 상류에서 "무엇이 존재하는가"만 정의하고, 하류가 식별자로 참조한다.

---

## 이 프로젝트에서 다루는 것

기능의 개수보다 **구조가 무너지지 않게 만드는 방법**에 초점을 두고 진행한다. 도메인 주도 설계의 전술 패턴을 적용하되, 규칙이 사람의 기억이 아니라 도구와 타입으로 지켜지도록 만드는 것이 목표다.

### 경계를 문서가 아니라 정적 검사로 강제한다

모듈끼리 무엇을 주고받을 수 있는지, 계층 간 의존이 어느 방향으로 흘러야 하는지를 정적 검사 규칙으로 못 박았다. 다른 모듈의 애그리거트를 참조하거나, 도메인이 인프라를 향하면 검사에서 걸린다.

규약을 문서로만 두면 지켜지지 않는다는 판단이었고, 실제로 규칙을 도입하자 도메인이 다른 모듈의 응용 계층을 참조하고 있던 경로가 드러났다.

→ [모듈 경계](./docs/architectures/module-boundaries.md) · [레이어](./docs/architectures/layering.md)

### 식별자를 서로 섞이지 않는 값 객체로 만든다

식별자를 원시 문자열로 두면 서로 다른 대상의 식별자가 뒤바뀌어도 아무도 알아채지 못한다. 종류마다 고유한 표식을 부여해 대입 자체가 막히게 했고, 타입 정보가 사라지는 경계를 지나온 값을 위해 실행 시점 검사도 함께 뒀다.

처음에는 표식 없이 제네릭만으로 구분하려 했는데, 밑에 깔린 타입이 모두 같아 아무것도 구분되지 않았다.

→ [식별자](./docs/architectures/domain-model.md#식별자)

### 도메인 모델과 저장 모델을 분리한다

저장 기술의 요구사항이 도메인 모델의 모양을 결정하지 않도록 두 모델을 나누고, 그 사이를 매핑 계층이 번역한다. 엔티티 생성자는 닫아 두고, 새로 만드는 경로와 저장된 상태를 되살리는 경로를 이름이 다른 팩토리로 분리했다.

→ [영속성 매핑](./docs/architectures/persistence-mapping.md)

### 저장 도구의 연쇄 저장을 쓰지 않는다

애그리거트를 저장할 때 무엇이 언제 저장되고 지워지는지가 코드에 드러나야 한다고 봤다. 저장 모델의 관계 필드는 조회로만 채워지고, 코드가 객체 그래프를 조립하는 입구 자체를 타입에서 없앴다.

같은 맥락에서, 조인되지 않은 관계를 만나면 빈 값으로 넘기지 않고 즉시 실패한다. 조인을 빠뜨린 실수가 "자식이 없는 애그리거트"로 위장되면 그 값이 저장 경로로 흘러가 실제 데이터를 지우기 때문이다.

→ [영속성 매핑](./docs/architectures/persistence-mapping.md)

### 판단의 근거를 남긴다

구조에 관한 결정을 채택한 것뿐 아니라 **기각한 대안과 그 이유까지** 기록으로 남긴다. 나중에 같은 선택지가 다시 올라왔을 때 왜 아니었는지 다시 따지지 않기 위해서다.

→ [결정 기록](./docs/dev-logs/adr.md)

## 기술 스택

TypeScript · NestJS · TypeORM · PostgreSQL · pnpm 워크스페이스 · Jest · ESLint / Prettier · Winston

## 구조

```
src/
├─ common/            여러 모듈이 공유하는 기반 타입과 유틸
├─ configs/           환경 변수 스키마
└─ modules/
   ├─ common/         설정·데이터베이스·로깅처럼 기능에 종속되지 않는 모듈
   └─ features/       기능 모듈. 애그리거트 루트 단위로 나뉜다
```

기능 모듈은 안쪽부터 식별자 · 도메인 · 응용 · 인프라 · 표현 계층으로 구성되고, 의존은 안쪽으로만 흐른다.

## 진행 방식

기능을 넓히기 전에 도메인 모델과 경계 규칙을 먼저 세우고 있다. 애그리거트와 영속성 매핑까지 자리를 잡았고, 응용 계층과 표현 계층은 그 위에 올린다.
