# 아키텍처 결정 기록

> 구조에 관한 결정과 그 근거를 쌓아 두는 곳. 최신 날짜가 위에 온다.
>
> 결정의 **내용**은 [아키텍처 문서](../architectures/CLAUDE.md)가 소유한다. 여기에는 **언제 왜 그렇게 정했는지**와 **무엇을 기각했는지**만 남긴다. 시간이 지나 뒤집힌 결정은 지우지 않고, 뒤집은 결정을 새 항목으로 추가한 뒤 원래 항목에서 그것을 가리킨다.

## 2026-08-20

상품 정보 도메인의 뼈대를 세우며 내린 결정들. 이 기록의 첫 항목이다.

### 서비스 범위를 상품 정보로 한정한다

**결정** — 판매 대상이 무엇인지 정의하는 일만 이 서비스가 소유한다. 수량과 가격, 그리고 판매 대상을 채널별로 묶어 진열하는 구성은 다른 서비스에 둔다. 서비스 간 참조는 이쪽이 소유한 식별자로 하며, 의존은 저쪽에서 이쪽으로만 향한다.

**배경** — 판매 단위에 수량과 가격을 붙일지 판단해야 했다. 두 관심사는 같은 대상을 가리키지만 변경 빈도와 동시성 특성이 전혀 다르다.

**기각한 대안** — 판매 단위에 수량·가격 속성을 함께 두는 안. 같은 사실이 두 곳에 존재하게 되어 어느 쪽이 진실인지 정할 수 없다.

**결과** — 판매 단위가 독립 애그리거트로 승격될 압력이 사라져 상위 애그리거트의 자식으로 확정됐다. 이 서비스에서 다른 서비스를 동기 호출하는 정책은 만들지 않는다. → [서비스 경계](../architectures/service-boundaries.md)

### 서비스 안을 애그리거트 루트 단위 기능 모듈로 나눈다

**결정** — 애그리거트 루트마다 모듈 하나를 기본값으로 두되, 모듈 하나가 루트를 여럿 가질 수 있다. 루트와 그 자식 엔티티는 반드시 한 모듈에 둔다.

**배경** — 한 모듈 안에 세 애그리거트가 모여 있었고, 이를 더 쪼갤지 판단해야 했다.

**기각한 대안**
- 별도 바운디드 컨텍스트로 분리 — 세 개념 모두 같은 사람이 같은 뜻으로 쓰고, 지켜야 할 검증이 경계를 가로지른다. 나누면 서로를 계속 호출하게 된다.
- 모듈도 나누지 않고 그대로 유지 — 이미 참조가 식별자로만 이뤄져 있어 분리 비용이 가장 낮은 시점이었다.

**결과** — 모듈 간 의존이 순환 없는 방향 그래프가 됐다. 모듈을 서비스로 승격하는 일이 경로 이동 수준으로 줄었다. → [모듈 경계](../architectures/module-boundaries.md)

### 모듈의 공개 표면을 정하고 린트로 강제한다

**결정** — 식별자·응용 계층·저장 모델·모듈 정의만 공개하고, 애그리거트와 매핑·저장소 구현은 감춘다. 이 경계를 린트 규칙으로 검사한다.

**배경** — 모듈을 나눠도 규약이 문서로만 존재하면 지켜지지 않는다.

**기각한 대안**
- 배럴 파일로 공개 표면을 표현 — 프로젝트가 배럴을 두지 않는 방침이다.
- 넓게 막고 예외를 되살리는 규칙 형태 — 상위 경로가 막히면 하위를 되살릴 수 없어 허용 목록이 통째로 무시됐다. 금지 경로를 명시적으로 나열하는 형태로 바꿔 해결했다.

**결과** — 저장 모델은 공개하되 매핑과 저장소 구현은 감추는 비대칭이 생겼다. 스키마 관계는 한 데이터베이스 안에서 어차피 존재하는 사실이지만, 도메인 타입을 다루는 것은 새어 나가면 안 되기 때문이다. → [공개 표면](../architectures/module-boundaries.md#공개-표면)

### 레이어 의존 방향을 안쪽으로 고정하고 린트로 강제한다

**결정** — 식별자에서 표현 계층까지 의존이 한 방향으로만 흐르게 하고, 이를 린트로 검사한다.

**배경** — 모듈 경계만으로는 한 모듈 안에서 도메인이 바깥 계층을 참조하는 것을 막지 못했다. 실제로 도메인이 다른 모듈의 응용 계층을 참조해도 통과하는 구멍이 있었다.

**결과** — 애그리거트 간 조율을 응용 계층에 두는 것이 규칙이 아니라 강제 사항이 됐다. 외부 시스템 의존도 포트와 어댑터로만 표현할 수 있다. → [레이어](../architectures/layering.md)

### 식별자를 종류별로 구분되는 값 객체로 만든다

**결정** — 식별자마다 고유한 표식을 부여해 서로 대입되지 않게 하고, 동치 비교에서 실제 종류까지 확인한다. 복제는 원래의 구체적인 종류를 유지한다.

**배경** — 밑에 깔린 타입이 같은 식별자들은 표식 없이는 구조적으로 완전히 동일해 서로 자유롭게 대입된다.

**기각한 대안** — 밑에 깔린 타입을 그대로 표식으로 삼는 방식. 모든 식별자가 같은 타입을 쓰고 있어 아무것도 구분하지 못했다.

**결과** — 컴파일 시점 구분에만 기대지 않고 실행 시점 검사를 함께 둔다. 타입 정보가 사라지는 경계를 지나온 값이 있을 수 있기 때문이다. → [식별자](../architectures/domain-model.md#식별자)

### 엔티티 생성 입구를 팩토리로 한정하고 생성 경로와 복원 경로를 나눈다

**결정** — 엔티티 생성자를 외부에 열지 않고, 새로 만드는 경로와 저장된 상태를 되살리는 경로를 이름이 다른 팩토리로 분리한다.

**배경** — 매핑이 엔티티를 만들어야 하는데 생성자가 닫혀 있었다. 두 경로를 한 입구로 합치면 복원할 때마다 불필요한 검증을 하거나 생성할 때 검증을 건너뛰게 된다.

**결과** — 호출자가 무엇을 하려는지 이름에 드러난다. 새로 만드는 경로는 아직 두지 않았고, 필요해질 때 같은 원칙으로 추가한다. → [생성 경로](../architectures/domain-model.md#생성-경로)

### 저장 모델의 관계는 조회로만 채우고, 애그리거트 저장은 저장소가 직접 수행한다

**결정** — 저장 도구의 연쇄 저장 기능을 쓰지 않는다. 저장 모델의 생성 입구는 원시 컬럼만 받고, 관계 필드는 전부 선택적으로 선언한다. 로드되지 않은 관계를 만나면 즉시 실패한다.

**배경** — 무엇이 언제 저장되고 지워지는지가 코드에 드러나지 않으면 의도하지 않은 삭제가 조용히 일어난다.

**기각한 대안**
- 로드되지 않은 관계를 빈 값으로 대체 — 조인을 빠뜨린 실수가 "자식이 없는 애그리거트"로 위장되고, 그 값이 저장 경로로 흘러가 실제 데이터를 지운다.
- 관계 필드를 일부만 선택적으로 선언 — 항상 로드된다고 가정한 관계에서 그 가정이 틀린 경로가 반드시 생긴다. 예외를 두지 않기로 했다.

**결과** — 도메인에서 저장 모델로 가는 변환이 루트에 해당하는 것만 만들어낸다. 저장소가 루트·자식·사라진 자식을 순서대로 직접 다뤄야 한다. 깊이를 알 수 없는 관계를 애그리거트에 담는 구조의 비용도 이 결정 때문에 드러난다. → [영속성 매핑](../architectures/persistence-mapping.md)

### 저장 모델의 모든 제약과 인덱스에 이름을 직접 짓는다

**결정** — 기본 키·외래 키·유일 제약·인덱스에 종류를 나타내는 접두사와 대상을 담은 이름을 붙인다. 테이블과 컬럼 이름도 전역 이름 전략에 맡기지 않고 항상 명시한다.

**배경** — 저장 도구가 지어 주는 이름은 규칙을 알 수 없는 문자열이라, 제약 위반이 났을 때 어떤 규칙에 걸렸는지 읽을 수 없고 마이그레이션에서 지목할 수도 없다.

**기각한 대안** — 기본값에 맡기고 필요할 때만 이름을 주는 안. 어떤 것이 명시적이고 어떤 것이 자동인지 구분되지 않아 결국 전부 확인해야 한다.

**결과** — 속성 이름을 바꿔도 제약 이름이 조용히 따라 바뀌지 않는다. 새 저장 모델을 추가할 때마다 지켜야 하는 규칙이 늘었으므로 형태를 문서로 고정했다. → [저장 모델 선언](../code-conventions/orm-entity.md#이름-규칙)

### 조인 정보를 참조 대상 속성에 붙이고 참조 쌍의 순서를 고정한다

**결정** — 조인 정보는 참조 대상 속성에 선언하고, 참조 대상 속성 다음에 외래 키 속성이 빈 줄 없이 따라온다. 관계 선언에 연쇄 저장 옵션은 켜지 않는다.

**배경** — 조인 정보가 외래 키 속성에 붙어 있었다. 저장 도구는 참조 대상 속성에서 그것을 찾으므로 선언이 무시되고 있었는데, 유도된 기본 컬럼 이름이 우연히 같아 동작에는 문제가 없어 드러나지 않았다. 제약 이름을 직접 지으려 하자 이름이 적용되지 않아 발견했다.

**결과** — 컴파일을 통과하고 동작까지 하지만 선언이 무시되는 형태가 있다는 것을 확인했다. 이런 종류는 어긋나기 전까지 드러나지 않으므로 금지 목록에 남겼다. → [참조 선언](../code-conventions/orm-entity.md#참조-참조-대상--외래-키)

### 인덱스를 붙이는 기준을 정한다

**결정** — 외래 키 컬럼과 조회 조건이 되는 컬럼에 인덱스를 붙인다. 복합 유일 제약의 앞쪽 컬럼과 본문성 컬럼에는 붙이지 않는다.

**배경** — 외래 키에는 인덱스가 자동으로 생기지 않아, 참조 대상을 지우거나 역방향으로 조회할 때마다 전체 탐색이 일어난다.

**기각한 대안** — 외래 키라면 예외 없이 인덱스를 붙이는 안. 복합 유일 제약이 이미 앞쪽 컬럼을 덮고 있는 경우 중복이라 쓰기 비용만 늘어난다.

**결과** — 유일해야 하는 값과 자주 찾는 값을 구분해서 판단한다. 중복을 막을 의도가 없으면 유일 인덱스를 쓰지 않는다. → [인덱스 붙이는 기준](../code-conventions/orm-entity.md#인덱스-붙이는-기준)

### 저장 모델 선언은 메타데이터 빌드까지 확인한다

**결정** — 저장 모델을 추가하거나 관계를 바꾼 뒤에는 컴파일에서 멈추지 않고 메타데이터가 실제로 만들어지는지 확인한다.

**배경** — 설정된 드라이버가 지원하지 않는 컬럼 타입이 선언되어 있었다. 컴파일과 정적 검사를 모두 통과했지만 연결 전 단계에서 실패하는 종류였다. 널 허용이 속성과 컬럼 사이에서 어긋난 것도 같은 방식으로 숨어 있었다.

**결과** — 선언 오류가 실행 시점이 아니라 작성 시점에 드러난다. 이 확인 단계를 컨벤션 문서의 마지막 절로 고정했다. → [선언한 뒤 확인할 것](../code-conventions/orm-entity.md#선언한-뒤-확인할-것)

### 예외에 이름을 붙인다

**결정** — 이름 없는 일반 예외 대신 상황을 나타내는 예외 타입을 정의해 던진다. 예외 계열은 누구의 잘못인가로 나눈다.

**배경** — 이름 없는 예외는 호출자가 무엇이 잘못됐는지 타입으로 구분할 수 없고, 응답 처리에서 일괄로 뭉뚱그려진다.

**결과** — 외부 입력 문제와 내부 호출 실수가 서로 다른 계열로 갈라져 다른 대응을 받는다. → [실패](../architectures/domain-model.md#실패)

### 로컬 실행 구성을 컨테이너 두 개로 고정한다

**결정** — 로컬에서는 서버 하나와 데이터베이스 하나를 각각 컨테이너로 띄운다. 데이터베이스 컨테이너는 로컬에만 존재하며 배포 대상이 아니다. 서비스는 접속 정보만 알고, 데이터베이스가 어디에 있는지는 주입으로 정해진다.

**배경** — 실제 환경의 데이터베이스는 서비스 바깥에서 관리된다. 로컬 편의를 위한 구성이 실행 환경 계약에 섞이면 두 환경이 갈라진다.

**기각한 대안** — 서버는 호스트에서 실행하고 데이터베이스만 컨테이너로 띄우는 안. 반복 속도는 빠르지만 실행 환경이 로컬에서만 달라져, 이미지가 실제로 도는지는 별도로 확인해야 한다.

**결과** — 로컬 구성 파일은 배포 경로에 관여하지 않는다. 컨테이너 안의 접속 대상만 주입으로 바꿔 끼우면 같은 서비스 정의가 두 환경에서 성립한다. → [로컬 실행](../operations/local-development.md)

### 상태 확인을 살아있음과 준비됨으로 가른다

**결정** — 상태 확인 경로를 둘로 나눈다. 살아있음은 프로세스 자신만 보고 의존성을 확인하지 않는다. 준비됨은 요청 처리에 필요한 의존성을 확인한다.

**배경** — 두 질문에 대한 실행 환경의 대응이 다르다. 하나는 프로세스를 교체하고, 다른 하나는 라우팅에서 뺀다.

**기각한 대안** — 경로 하나에서 의존성까지 확인하는 안. 데이터베이스가 잠시 흔들리면 모든 인스턴스가 동시에 재시작을 반복하게 된다. 실제로 데이터베이스를 내렸다가 올려 보면 프로세스를 살려 둔 쪽은 재시작 없이 스스로 회복한다.

**결과** — 의존성 장애가 가용성 저하로 끝나고 재시작 폭풍이 되지 않는다. 의존성을 어느 쪽에 넣을지가 판단 기준이 됐다. → [상태 확인](../operations/runtime-contract.md#상태-확인)

### 설정 주입 경로를 환경에 따라 가른다

**결정** — 로컬과 테스트 환경에서만 파일에서 설정을 읽고, 그 밖에서는 프로세스 환경으로 주입받는다. 이미지에는 환경별 값이 담기지 않는다.

**배경** — 파일을 항상 읽는 구성이었는데, 실제 환경에는 그 파일이 없다. 없는 파일을 조용히 넘기는 동작이라 설정이 비어 있어도 기동 직전까지 드러나지 않았다.

**결과** — 이미지가 환경과 무관해졌다. 이 저장소가 배포에 내놓는 것은 이미지와 설정 키 목록, 그리고 동작 약속 세 가지로 정리됐고 배포 명세 자체는 저장소 밖에 둔다. → [실행 환경 계약](../operations/runtime-contract.md)

### 스키마 생성을 로컬에 한정한다

**결정** — 저장 모델 선언으로부터 스키마를 만드는 동작은 로컬에서만 켠다. 다른 환경에서 서비스는 자기 스키마를 만들지 않고, 이미 존재하는 스키마에 붙는다.

**배경** — 모델이 아직 자주 바뀌는 시기라 로컬에서는 선언과 스키마가 자동으로 맞춰지는 편이 빠르다. 그러나 같은 동작이 데이터가 있는 환경에서 돌면 선언과 다른 것을 지운다.

**결과** — 서비스가 스키마의 주인이 아니라는 것이 계약으로 고정됐다. 스키마를 바꾸는 방법은 이 결정과 분리해서 정한다. → [스키마](../operations/runtime-contract.md#스키마)
