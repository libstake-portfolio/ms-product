# 영속성 매핑

> 도메인 모델과 저장 모델을 어떻게 분리하고 오가는지.

---

## 두 모델을 분리하는 이유

도메인 모델은 **규칙**을 담고 저장 모델은 **스키마**를 담는다. 하나로 합치면 저장 기술의 요구사항이 도메인 모델의 모양을 결정하게 된다. 식별자를 원시 타입으로 눕히고, 생성자를 열고, 모든 필드를 변경 가능하게 만드는 압력이 전부 저장 쪽에서 온다.

둘 사이의 번역은 **매핑 전용 구성 요소**가 담당한다. 도메인은 저장 모델의 존재를 모르고, 저장 모델은 도메인 타입을 참조하지 않는다.

## 저장 모델의 관계 필드

저장 모델은 두 종류의 필드를 갖는다.

- **원시 컬럼** — 조회하면 항상 채워진다. 참조 관계의 외래 키도 여기에 속한다.
- **관계 필드** — 조회 시 함께 가져올 수도, 가져오지 않을 수도 있다.

관계 필드는 **선택적으로 선언한다. 예외를 두지 않는다.** 어떤 관계는 항상 로드된다고 가정하는 순간, 그 가정이 틀린 경로에서 조용히 잘못된 값이 만들어진다.

관계 필드는 **조회로만 채워진다.** 코드가 관계 필드에 값을 넣는 입구를 만들지 않는다. 저장 모델의 생성 입구는 원시 컬럼만 받는다. 이 제약이 아래의 명시적 저장 규칙을 구조적으로 보장한다.

## 애그리거트 저장은 명시적으로

저장 도구가 제공하는 연쇄 저장 기능에 기대지 않는다. 무엇이 언제 저장되고 지워지는지가 코드에 드러나지 않으면, 의도하지 않은 삭제가 조용히 일어난다.

저장소는 **루트와 자식을 각각 다룬다.** 루트를 저장하고, 자식을 저장하고, 사라진 자식을 정리하는 일을 순서대로 직접 수행한다.

이 때문에 도메인에서 저장 모델로 가는 변환은 **루트에 해당하는 것만** 만들어낸다. 자식은 별도의 변환으로 얻는다. 관계 필드를 비워두는 것과 빈 컬렉션으로 채우는 것은 다르다. 채워진 빈 컬렉션은 연쇄 저장이 켜졌을 때 자식 전체 삭제로 해석될 수 있다.

## 로드되지 않은 관계

애그리거트를 복원하려면 그 애그리거트에 속한 자식이 함께 조회되어 있어야 한다.

관계가 로드되지 않았다면 **즉시 실패한다.** 빈 컬렉션으로 대체하지 않는다. 조인을 빠뜨린 실수가 "자식이 없는 애그리거트"로 위장되면, 그 값이 저장 경로로 흘러가 실제 데이터를 지운다.

이 실패는 프로그래밍 실수이지 사용자 입력 문제가 아니므로, 그에 맞는 계열의 [이름 있는 예외](./domain-model.md#실패)로 표현하고 어떤 관계가 빠졌는지 알린다.

## 애그리거트 로드 단위

애그리거트는 로드와 저장의 단위다. 여기에 깊이가 정해지지 않은 구조를 담으면 한 번의 조회가 얼마나 커질지 예측할 수 없다.

깊이를 알 수 없는 관계는 애그리거트 안에 두지 말고, 참조 관계로 표현한 뒤 **탐색은 별도의 읽기 모델**에 맡긴다. 쓰기 모델은 불변식을 지키는 데 필요한 최소 범위만 담는다.

## 모듈 경계와의 관계

저장 모델은 모듈의 [공개 표면](./module-boundaries.md#공개-표면)에 포함된다. 스키마 수준의 관계는 한 데이터베이스 안에서 어차피 존재하는 사실이고, 매핑이 원시 컬럼만 읽어 도메인으로 넘기므로 다른 모듈의 저장 모델을 참조해도 도메인까지 결합이 번지지 않는다.

같은 이유로 매핑과 저장소 구현은 공개하지 않는다. 그것들은 도메인 타입을 다루므로, 공개하면 애그리거트가 모듈 밖으로 새어 나간다.
