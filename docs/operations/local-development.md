# 로컬 실행

> 로컬에서 서비스를 띄우고 동작을 확인하는 방법. 실행 환경이 지켜야 할 약속은 [실행 환경 계약](./runtime-contract.md)이 소유한다.

---

## 구성

컨테이너 두 개가 뜬다. 서버 하나와 데이터베이스 하나다.

데이터베이스 컨테이너는 **로컬에만 존재한다**. 다른 환경에서는 서비스 바깥의 관리형 데이터베이스에 붙으므로, 로컬 구성은 배포 대상이 아니다. 서비스가 데이터베이스에 대해 아는 것은 접속 정보뿐이고, 그것이 어디서 오는지는 [설정 주입](./runtime-contract.md#설정)이 정한다.

## 준비

로컬 환경 파일이 필요하다. 만드는 방법과 채워야 할 키는 [환경 파일 안내](../../envs/README.md)가 소유한다.

여기서 정한 데이터베이스 자격 증명은 두 곳에 함께 쓰인다. 서버가 접속할 때 쓰고, 로컬 데이터베이스가 **처음 기동할 때** 그 값으로 계정과 데이터베이스를 만든다. 이미 만들어진 뒤에 값을 바꾸면 서버만 새 값을 쓰게 되어 접속이 실패한다. 이때는 데이터를 버리고 다시 만들어야 한다.

## 실행

```bash
pnpm local:up      # 두 컨테이너를 띄운다
pnpm local:down    # 내린다
```

서버는 데이터베이스가 접속을 받을 수 있게 된 뒤에 기동한다. 소스는 컨테이너 안으로 연결돼 있어, 파일을 고치면 서버가 스스로 다시 시작한다.

쓰려는 포트가 이미 점유돼 있으면 로컬 환경 파일에서 그 포트를 바꾼다.

## 확인

상태 확인 경로 두 개로 확인한다. 각각이 무엇을 답하는지는 [상태 확인](./runtime-contract.md#상태-확인)이 소유한다.

```bash
curl localhost:3000/health/live
curl localhost:3000/health/ready
```

데이터베이스만 내려 보면 둘의 차이가 드러난다. 살아있음은 그대로 성공하고, 준비됨만 실패한다. 데이터베이스가 돌아오면 서버를 다시 시작하지 않아도 준비됨이 회복된다.

## 스키마

로컬에서는 서버가 기동할 때 저장 모델 선언으로부터 스키마를 만든다. **이 동작은 로컬에서만 켠다.** 다른 환경에서 서비스는 자기 스키마를 만들지 않는다.

데이터는 볼륨에 남아 컨테이너를 내려도 유지된다. 처음 상태로 되돌리려면 볼륨까지 지운다.

```bash
docker compose down --volumes
```
