# 명세 작성 가이드

> 이 영역의 문서를 누구의 자리에서, 어떤 모양으로 쓰는지.
>
> 문서 전반의 작성 규칙과 이 영역에 적용되는 예외는 [작업 대원칙 §0.9](../../CLAUDE_ko.md)가 소유한다.

---

## 기획자의 자리에서 쓴다

명세를 쓰는 사람은 개발자가 아니라 **서비스 기획자**다. 무엇이 필요한지까지 말하고, 그것을 어떻게 만드는지는 말하지 않는다. 만드는 방법은 받는 쪽이 정한다.

| 적는다 | 적지 않는다 |
| --- | --- |
| 무엇이 되어야 하는가 | 무엇으로 만들 것인가 |
| 어떤 순서로 일어나는가 | 어디에 어떻게 저장되는가 |
| 무엇이 막혀야 하는가 | 그것을 어떻게 막을 것인가 |
| 그래서 무엇이 함께 일어나야 하는가 | 그 소식이 어떤 방식으로 전달되는가 |

구현 사정 때문에 어려운 요구가 있다면 그건 받는 쪽이 되짚어 물을 일이지, 미리 접어 두고 쓸 일이 아니다. 기술적 제약을 짐작해 요구를 줄이면 그 판단이 어디에도 남지 않는다.

## 문서를 나누는 축

명세는 개념 단위로 나누지 않는다. 한 문서는 **운영자가 수행하는 하나의 업무**를 다루고, 그 업무가 여러 개념을 가로지르면 한 문서 안에서 가로지른다.

개념 단위로 나누면 여러 개념에 걸친 정책이 문서마다 복제되고, 어느 쪽이 진짜인지 정할 수 없게 된다.

## 문서의 골격

| 절 | 내용 |
| --- | --- |
| 이 문서가 다루는 업무 | 누가, 어떤 상황에서 하는 일인가 |
| 흐름 | 평문으로 서술한다. 상태가 오가면 상태도를, 화면이 필요하면 예시를 곁들인다 |
| 지원해야 하는 기능 | 무엇이 되어야 하고 무엇이 막혀야 하는가 |
| 파급 | 이 기능 때문에 다른 곳에서 일어나야 하는 일 |
| 다루지 않는 것 | 범위 밖 항목과 그것을 다루는 문서로의 링크 |

파급 절이 비어 있는 명세는 절반만 쓰인 것이다. 어떤 기능이 지원되어야 하는가만큼, 그 기능이 무엇을 일으켜야 하는가가 명세의 몫이다.

## 용어를 지어내지 않는다

업계 관계자가 그대로 알아듣는 말을 쓴다. 새 말을 만들어야 할 것 같으면 대개 개념이 덜 정리된 것이지 말이 없는 것이 아니다.

정한 말은 [용어](./glossary.md)에 등록하고, 명세와 회의와 코드가 모두 같은 말을 쓴다. 한 개념을 자리마다 다르게 부르기 시작하면 같은 것을 말하고 있는지 확인할 방법이 없어진다.

## 빈 곳을 남긴 채 넘어가지 않는다

명세가 답하지 않은 것은 결국 만드는 자리에서 정해진다. 그렇게 정해진 것은 어디에도 남지 않아서, 나중에 그것이 의도였는지 우연이었는지 가릴 수 없다.

정해지지 않은 것을 발견하면 추측으로 메우지 말고 묻는다. 특히 아래가 자주 빈다.

| 확인할 것 | 묻는 말 |
| --- | --- |
| 막히는 경우 | 이 동작이 되지 않아야 하는 때는 언제인가 |
| 되돌리는 길 | 잘못했을 때 무르는 방법이 있는가 |
| 겹침 | 이 값이 다른 것과 같아도 되는가, 같으면 안 된다면 어느 범위에서 |
| 개수 | 몇 개까지 만들 수 있는가 |
| 없는 것을 지목했을 때 | 대상이 존재하지 않으면 어떻게 되는가 |
| 딸려 오는 변화 | 이 일이 일어나면 다른 무엇이 함께 바뀌어야 하는가 |

## 그 밖의 규칙

- **수치는 명세가 소유한다.** 개수 상한처럼 숫자로 적히는 정책은 기획 결정이다. 코드는 그 값을 옮겨 담을 뿐이다.
- **현재형으로 쓴다.** 구현이 되었는지, 언제 되는지는 명세가 답하지 않는다.
- **그림은 문서 안에 둔다.** 별도 이미지 파일로 빼면 본문과 따로 낡는다.
- **화면 예시는 약속이 아니다.** 이 서비스는 화면을 소유하지 않는다. 예시는 어떤 기능이 필요한지를 보이는 도구로만 쓴다.

명세를 언제 확정된 것으로 보는지는 [작업 대원칙 §1.3](../../CLAUDE_ko.md)이 소유한다.
